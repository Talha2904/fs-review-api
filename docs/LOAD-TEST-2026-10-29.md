# Load test with 50 funds, 29 Oct 2026

Phase 7 (plan section 9). The aim was to see whether the api stays responsive for a firm with 50 funds in
review at once, and to find what breaks first.

## How it was run

`npm run load-test` (`scripts/load-test.ts`) starts the api in its own process against an empty, migrated
database made for the test. It fills that database through the HTTP api, the way the screens do:

- one client with 50 funds, each with a Preparer, Reviewer and Manager;
- the four sample documents attached to every fund and marked ready;
- an analysis of every fund, run as background jobs with 4 workers;
- 12 manual review points per fund, each with a comment, and a response on every third.

That gives 950 points and 2,700 thread messages. Every point is open and assigned to the one Preparer, which
is harder on the bell than a real firm, where most points are cleared and spread across people.

It then times the reads the screens make most: 10 requests per person, first one person at a time, then 20
people at once. Twenty at once is the burst that follows a change, when every open tab refetches.

```bash
LOAD_DATABASE_URL=postgresql://fsreview:...@localhost:5432/fsreview_load npm run load-test
```

Machine: a laptop with a 12th Gen Intel Core i5-1235U (12 threads), Postgres 16 in Docker on the same
machine. A hosted database adds network time to every query, so treat the figures as relative.

## Results after the fixes

Seeding took 29 seconds; the 50 analyses took 3.8 seconds with 4 workers.

| Read                                         | People at once | p50 ms | p95 ms | Response KB |
| -------------------------------------------- | -------------: | -----: | -----: | ----------: |
| Portfolio (`GET /api/portfolio`)             |              1 |     28 |     34 |          24 |
| Bell (`GET /api/notifications`)              |              1 |    142 |    159 |          34 |
| One fund (`GET /api/engagements/:id/review`) |              1 |     31 |     44 |          69 |
| Fund list (`GET /api/engagements`)           |              1 |     19 |     22 |          17 |
| Portfolio                                    |             20 |    324 |    367 |          24 |
| Bell                                         |             20 |  1,955 |  2,085 |          34 |
| One fund                                     |             20 |    324 |    360 |          69 |
| Fund list                                    |             20 |    130 |    146 |          17 |

`GET /api/reviews`, which returns every fund's whole review, took 231 ms for one person and 3.4 seconds at 20,
with a 2 MB response. No screen calls it since the portfolio and the bell moved to the api; it stays for
integrations.

## What the test found and what changed

| #   | Finding                                                                                                                                                                                                                         | Change                                                                                                                                                                                                                               | Test                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| L1  | Starting analyses of different funds at the same moment failed. The serializable transaction that stops two jobs for one fund also conflicted across funds, and the api answered "An analysis of this fund is already running." | A write conflict is retried with a short random wait, up to 8 times. A second start for the same fund then finds the first job and is refused, as before.                                                                            | `test/integration/PrismaAnalysisJobRepository.test.ts`                             |
| L2  | The bell built every fund's whole review (all documents, points with their full content, every message, checklists, reports) for each request: 250 KB per response and 2.8 s at 20 people.                                      | The bell has its own read model: point titles from a new `title` column, messages only on the person's own points from the last 90 days, nothing else. The bell lists the newest 50 actions and the total count. 34 KB per response. | `test/integration/PrismaPortfolioReadModel.test.ts`, `test/http/portfolio.test.ts` |
| L3  | After any change, every open tab refetched the portfolio and the bell 400 ms later, all together.                                                                                                                               | Each tab waits a random 0.4 to 2.4 seconds, so the requests reach the api spread out.                                                                                                                                                | `react-app/src/lib/useLive.js`                                                     |

The migration `20261028205739_phase7_point_title` adds the column and fills it from each point's content.

## What it means

- One person waits under 50 ms for the portfolio and one fund, and about 150 ms for the bell.
- Twenty people polling every 30 seconds make under one bell request a second. The api serves about ten a
  second for this worst-case Preparer, so there is room for bursts.
- A burst of 20 at once still queues for up to 2 seconds. Most of the bell's time is Prisma turning 950 point
  rows and 2,700 messages into objects, because every point is open and assigned to the same person.

## Limits to watch

- **Cleared points accumulate.** The bell still reads every point's status and people, so its cost grows with
  the firm's history. If a firm reaches tens of thousands of points, leave out the points of signed-off funds.
- **One api instance.** The figures are for one process. A second instance needs the Redis event bus first
  (plan section 7.6).
- **Web bundle.** The front end is 3.1 MB before compression, 945 KB compressed, mostly the spreadsheet
  library and the app in one file. Splitting the Finance and Administrator screens out would cut the first load.
